## 一、微信 4.x 为什么要「只能开一个」

微信 4.x 是 Qt 自绘界面的客户端。启动流程大致是：

```
Weixin.exe（外壳启动器）
    ├─ 读自己所在目录下的版本库目录（形如 4.1.15.56）
    ├─ 加载 Weixin.dll（真正的业务逻辑，约 200 MB）
    ├─ 确定配置根：SHGetKnownFolderPath(RoamingAppData)
    ├─ 确定数据根：读配置里的 51a1fffe…ini
    └─ 起 5 个左右的子进程（主进程 + 渲染 + 网络 + 崩溃收集…）
```

其中「配置根」这一步是关键：

> `SHGetKnownFolderPath(RoamingAppData)` 会**展开当前进程环境块里的
> `%USERPROFILE%\AppData\Roaming`**。

也就是说，**微信的配置位置完全由 `USERPROFILE` 决定**。
两个进程如果 `USERPROFILE` 相同，微信就认为它们是「同一个用户」，
于是第二个要么被判定成重复运行而退出，要么直接抢第一个的配置。

## 二、我们怎么绕开的

既然配置位置跟着 `USERPROFILE` 走，那就给每个实例一个**自己的 `USERPROFILE`**：

```
实例 A:  USERPROFILE = D:\WeChatMulti\A\Profile
实例 B:  USERPROFILE = D:\WeChatMulti\B\Profile
```

于是在微信眼里，A 和 B 就是两个不同的用户，各自有独立的配置、
独立的登录态、独立的聊天数据。

再加上**独立的数据根**（聊天记录的实际存放位置）：

```
<实例>\Profile\AppData\Roaming\Tencent\xwechat\config\51a1fffea11325a1e4104c6b3de47af7.ini
    内容就是一行绝对路径：D:\WeChatMulti\A\Data
```

微信读到这个 ini，就把聊天记录、插件、图片全部写到 `D:\WeChatMulti\A\Data` 去。

### 为什么要设五个环境变量

| 变量 | 作用 | 不设会怎样 |
|---|---|---|
| `USERPROFILE` | 配置根的根 | 配置写回主账号目录，**两个号互相覆盖** |
| `APPDATA` | 配置根 | 同上 |
| `LOCALAPPDATA` | 本地缓存 | 缓存串号 |
| `TEMP` / `TMP` | 临时文件 | 临时文件串号，偶发崩溃 |

**一个都不能少。** 早期版本只设了 `USERPROFILE`，结果 `APPDATA` 还是指向
主账号，两个号互相踢下线 —— 排查了很久。

### 为什么还要 `HOMEDRIVE` / `HOMEPATH`

有些程序不读 `USERPROFILE` 而读 `HOMEDRIVE` + `HOMEPATH`。
微信自身不一定用，但插件、崩溃收集器、某些 shell 扩展会用。
一起设上更稳，代价为零。

## 三、启动器脚本

每个实例对应一个 `.bat`（由 `core.make_launcher()` 生成）：

```bat
@echo off
set "WX_HOME=D:\WeChatMulti\B"
if not exist "%WX_HOME%\Weixin.exe" goto :missing

set "USERPROFILE=%WX_HOME%\Profile"
set "APPDATA=%WX_HOME%\Profile\AppData\Roaming"
set "LOCALAPPDATA=%WX_HOME%\Profile\AppData\Local"
set "TEMP=%WX_HOME%\Profile\AppData\Local\Temp"
set "TMP=%TEMP%"
set "HOMEDRIVE=D:"
set "HOMEPATH=\WeChatMulti\B\Profile"

rem  防重复启动：本实例已在跑就退出
"%WX_PY%" "wx_instance_guard.py" "%WX_HOME%\Profile" >nul 2>&1
if errorlevel 1 (
    start "" "%WX_HOME%\Weixin.exe"
)

:tag
call "tag_wx_windows.bat" --watch 40
exit /b 0
```

### 三个容易踩的坑

**① 批处理模板不能用 `%` 格式化。**
`.bat` 里满是 `%VAR%`、`%~1`、`%ERRORLEVEL%`。
用 Python 的 `%` 格式化就得处处写 `%%`，漏一个就出错。
正确做法是 `.replace()` + `@TOKEN@` 占位：

```python
tpl = '"@GUARD@" "%WX_HOME%\\Profile" >nul 2>&1\nif errorlevel 1 (\n    start "" "%WX_HOME%\\Weixin.exe"\n)'
return tpl.replace("@GUARD@", GUARD)
```

**② `.bat` 必须是 CRLF 行尾。**
LF 行尾的 bat 在某些环境下会执行出错。

**③ 含中文路径的 `.bat` 要用 GBK 编码写。**
用 UTF-8 写会让 cmd 显示乱码，路径里有中文时可能直接找不到文件。

## 四、防重复启动：读 PEB

「这个实例是不是已经在跑了」需要能判断「某个微信进程属于哪个实例」。

### 为什么不能用常规办法

- **窗口标题**：可以改，而且用户自己也能改 —— 不可靠
- **日志文件独占锁**：微信并不总是持锁，会误判成「没在跑」
- **UIAutomation**：微信 4.x 是 Qt 自绘 UI，主窗口的 UIA 子节点数为 **0**，
  自动化框架完全看不到它

### 解法：读进程 PEB 里的环境变量

每个进程的 `PEB → ProcessParameters → Environment` 里存着它自己的
环境块。`USERPROFILE` 就在里面 —— 而且**每个实例的值都不一样**。

x64 下的偏移：

```
PEB.ProcessParameters                        = 0x20
RTL_USER_PROCESS_PARAMETERS.Environment      = 0x80
```

（注意 `Environment` 是 **0x80**，不是 0x88 —— 0x88 是 `EnvironmentSize`。）

拿到环境块后，在里面找 `USERPROFILE=` 这一段，读出等号后面的值。

于是「这个 PID 属于哪个实例」就变成了一次字符串比较：
**100% 准确，不依赖任何可被篡改的东西。**

`wechatmulti/guard.py` 就是干这个的，退出码约定：

| 退出码 | 含义 |
|---|---|
| 0 | 该实例正在运行 |
| 1 | 该实例没在运行 |
| 2 | 出错 |

## 五、窗口打标

三个实例的窗口标题都是「微信」，任务栏上分不清。
`wechatmulti/tagger.py` 定期枚举窗口，把标题改成 `微信A` / `微信B`：

```python
PROFILE_RE = re.compile(r"\\([A-Za-z])\\Profile$", re.IGNORECASE)
```

从窗口所属进程的 `USERPROFILE` 反推出实例代号。

> 早期版本把目录名写死成 `Profile`，后来改成正则匹配 ——
> 因为 `Profile` 只是个约定，用户完全可以把目录改名。

## 六、历史包袱：二进制补丁

### 早期方案

微信 4.x 早期版本的单实例判定是**全局进程检查**，光改 `USERPROFILE` 不够，
必须改二进制。补丁点是启动器里的三个跳转：

| 补丁点 | 原始指令 | 改后 | 作用 |
|---|---|---|---|
| ① | `jne +0x1a` | `jmp +0x1a` | 无条件跳过 |
| ② | `test al,al / jnz +9` | `mov al,1 / jmp +9` | 永远走「已存在」分支 |
| ③ | `jnz <rel32>` | `nop / jmp <rel32>` | 跳到同一目标 |

三处都是**等长替换**，不改指令边界、不改跳转目标。

补丁点在不同微信版本里的偏移不一样，每次编译代码布局都会变。
所以匹配时不能写死偏移，而要拿「补丁点前后的代码特征」去匹配，
并且把**重定位相关的字节挖空**（`call`/`jmp`/`lea`/`cmp [rip+x]` 的位移）：

```python
_REL_PREFIX = [b"\xe8", b"\xe9", b"\x0f\x85", b"\x48\x8d", ...]

def _mask_holes(seg):
    holes = set()
    for i in range(len(seg)):
        for pre in _REL_PREFIX:
            if seg[i:i+len(pre)] == pre:
                d = i + len(pre)
                holes.update(range(d, d+4))
                break
    return holes
```

### 为什么现在不用了

实测（微信 4.1.15.56，2026-10-30，沙箱内两轮交叉验证）：

- **官方启动器原样就能拉起独立实例** —— 主实例在跑的情况下照样起得来；
- 打补丁的版本同样能起来，但**没有任何额外收益**。

新版微信的单实例判定已经改为**基于用户目录**。

### ⚠️ 那次「补丁导致崩溃」的误判

中途出现过一个结论：「打补丁后的 4.1.15.56 启动器启动即崩」，
并据此差点放弃新版支持。**这个结论是错的**，错在实验设计：

1. **实验时本机有 15 个微信进程在跑**（主实例 + 两个多开实例）。
   单实例门把**所有**新启动都挡住了 —— 连**未打补丁**的官方启动器
   都返回 `-1`。于是「orig 也失败」被误读成「补丁把程序改崩了」。
2. 退出码 `-1` **无法区分**「崩溃」和「被门挡后干净退出」。

**正确判据**是「这个实例自己的进程有没有冒出来」，而不是退出码。

重做实验（清空其他实例 + 完整复制版本库 + 两种顺序各跑一轮）后，
orig 和 patched **都能**成功拉起独立实例。

**教训**：多实例场景下测「能不能启动」，判据必须看**实例自己的进程**，
而且**实验必须在干净环境里做**。

### 教训沉淀成代码

`wechatmulti/sandbox.py` 就是为此写的：

- 所有实验只在路径带 `_sandbox_` 标记的目录里跑
- `assert_sandbox()` 会拒绝 `D:\WeChatMulti\B`、`C:\Program Files\Tencent\Weixin`、
  `E:\WEIXIN` 等真实位置
- 模块里**不提供任何 kill 能力**，只读不杀
- 判据函数 `watch_sandbox_pids()` 只认自己沙箱的 profile

## 七、目录布局

```
D:\WeChatMulti\
├── 微信多开管家.exe
├── 微信多开安装器.exe
├── wxguard.exe
├── wxtag.exe
├── instances.json          实例清单（明文，可手工编辑）
├── A\                      实例 A 的程序文件
│   ├── Weixin.exe          ← 官方那份，原样复制
│   ├── 4.1.15.56\         ← 版本库，完整复制
│   │   ├── Weixin.dll      （约 200 MB）
│   │   └── ...
│   ├── Profile\            ← 配置（USERPROFILE 指向这里）
│   │   └── AppData\Roaming\Tencent\xwechat\config\51a1fffe….ini
│   └── Data\               ← 某些旧实例的数据在这里（不推荐）
└── Data\A\                 ← 实例 A 的聊天数据（推荐位置）
    └── xwechat_files\
        ├── all_users\
        └── wxid_xxxxxxxx\
```

### 两条铁律

**① 版本库必须真复制，不能用硬链接。**
微信更新时会就地改写版本库里的文件。硬链接会让**所有实例**一起被改坏。

**② 数据根必须在程序目录外面。**
否则删除实例会连聊天记录一起删。代码里有 `Instance.data_inside_home` 专门防这个。

## 八、模块分工

| 模块 | 职责 |
|---|---|
| `core.py` | 实例模型、目录规划、启动脚本生成、进程归属判定、实例清单 |
| `finder.py` | 自动定位本机已装的官方微信（注册表 → 常见目录） |
| `installer.py` | 安装器：选目录、复制程序文件、铺工具、写数据根 |
| `gui.py` | 管家界面：实例列表、工具箱、使用引导 |
| `guard.py` | 防重复启动：读 PEB 判定实例归属 |
| `tagger.py` | 窗口打标 |
| `patcher.py` | **已停用**的历史补丁器（留作参考） |
| `sandbox.py` | 实验安全护栏（只读不杀 + 路径断言） |
